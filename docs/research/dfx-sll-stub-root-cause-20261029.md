# DFX 接口 SLL STUB：定位、修复方向与验证范围

日期：2026-10-29。对象：GETRF / U250 / 12 ns，E2 与双模块增量编译的集成版本。

## 结论

原先那 100 根 SLL 并不是增量编译新产生的错误连线。它们在**全量布线结果中已经是无有效接收端的 STUB 支路**；清除旧 RM 时被释放。恢复这些无效支路不是正确修复。

本次已直接复现：普通树形 `FIXED_ROUTE` 导入后保持了计划的 SLL—接收端关系，执行 `route_design` 后 DFX 接口树被改写，计划 SLL 留成 STUB，接收端改经其他 SLL。Vivado 仍可能报告这些 net 为 `ROUTED`。具体变化发生在 `route_design` 调用内；尚未定位到 Vivado 内部哪一个路由子阶段，也不声称掌握其源码规则。

这是当前 **E2 导出器与 DFX 接口物理分段的兼容性缺口**。不能把它归因于增量阶段 SLL 数量优化，也不能仅凭约束导入成功或资源 `IS_USED=1` 判定计划已落实。

## 原有证据与本次复现

原全量结果有 94 条接口 net 的计划/实际路径不一致。全量 → 静态 shell 释放的 100 根物理 SLL 来自其中 83 条 net；这 100 根全部是计划资源，且在保存的 ROUTE 和 FIXED_ROUTE 文本中均只出现在 STUB 支路。最终增量的 SLL 集合与 shell 相同。

本次选择三条实际接口 net，覆盖：

| 样本 | 类型 |
|---|---|
| `kernel/matA_U/q1[10]` | 静态驱动，含 RP 内接收端和静态接收端 |
| `.../grp_subUpdate_double_2_512_s_fu_5268/.../A_address1[2]` | RP 内驱动，含静态远端接收端 |
| `.../s_reg_11324_reg[1]_rep__0_n_3` | 高扇出，混合静态/RP 接收端，计划跨两道 SLR 边界 |

三条原约束在导入后均未出现 STUB，布线后均被原路径审计拒绝。对这三条 net 去除约束、保持位置和时钟的负对照全部布通、STUB 为 0；实际 SLL 数分别为 1、1、2。负对照检查了 523 个端点相关 cell 的 LOC、BEL、LOCK_PINS，以及时钟周期，均保持不变。

这些是局部 `route_design -nets` 诊断，不是新的 GETRF 全量 QoR 对照。该命令默认不做通常全设计路由的时序优化，因此不能据此比较完整设计 WNS 或运行时间。

## 代码缺口在哪里

基于 `519c537` 的代码：

- `scripts/dfx_sll.tcl::apply_full` 允许 DFX routing 后，仍直接调用普通 `e2_sll::apply_parallel`。
- `scripts/sll_routes.tcl::children` 把计划表示成 `GAP → SLL segment → GAP → leaf site pin`，没有表达物理 partition pin 及其静态/动态侧归属。
- 增量内部 net 的 `validate_internal_net` 已限制为活动 RP 内部；本次问题来自**全量 DFX 接口**，不是这项内部 net 范围保护失效。
- `e2_sll::audit` 已检查 STUB、实际 SLL 集合和逐接收端路径。它之前正确拦截了问题。上轮继续增量来自用户明确授权的 `record-failure` 实验流程，不是审计通过。

DFX 接口必须经过 partition pin，且该点用于保持不同 RM 之间的静态接口一致性。这使它不同于普通扁平 net。参见 [AMD UG909：Partition Pins](https://docs.amd.com/r/en-US/ug909-vivado-partial-reconfiguration/Partition-Pins)。

## 修复应如何做

### 1. 在全量布线前，按物理 partition pin 拆分接口

两种基本方向：

```text
静态驱动 → [静态路由段：SLL → partition pin] → [动态路由段：RP 接收端]
RP 驱动 → [动态路由段：partition pin] → [静态路由段：SLL → 静态接收端]
```

对于混合扇出和多个 RP，先按真实 RP 端口/物理 partition pin 分组，再在各物理段内保留共享树。不能简单把全部 RP 接收端替换成一个任意 partition pin，也不能把同一条网名的不同物理段当成互不相关的 net。

静态/动态归属要由实际物理段确定，不能把接口 net 的全部 SLL 一律视为静态资源；若 RP 本身跨 SLR，其动态内部段也可能需要 SLL。

放置后，`HD.ASSIGNED_PPLOCS` 可能仍只有 tile 信息；不能把 tile 字符串当成已选定的具体路由节点。需要先由原生接口处理落实实际节点，再生成/校验接口静态段。

### 2. 让指定 SLL 处在连接有效终点的静态树中

已验证的简单输入接口修复：把计划 SLL 出口到实际 partition pin 的 GAP 补成连续路径，保留驱动侧与 RP 接收侧的普通路由选择。`q1[10]` 使用原计划 `LAG_LAG_X60Y258/UBUMP19`，STUB 消失，原有逐接收端 SLL 审计通过。

反方向仅补 `partition pin → SLL 入口` 不够：SLL 出口仍可能成为死支路。因此通用接口方案需要保证含 SLL 的静态段到有效静态终点/partition pin 连续，并逐接收端验证。

这会额外固定部分普通布线。它不是“仍只锁五个 SLL 节点”的等价实现，必须单独记录固定范围和生成时间；不能悄悄当作原来的纯 SLL 约束。

本次提供的候选构造器采用实际路由图搜索、按 SLL 序列防止不同接收端组错误合流、合并同组共享路径，并裁去无终点的普通分支。路由图中未占用的 site 输入/时钟节点也不能任意作为数据线中继，需要保留其逻辑用途。

### 3. 通过验收后才封存静态 shell

验收至少包含：

1. net 完整布通，且无节点冲突；
2. 计划 SLL 位于目标接收端的有效路径上，而不只是出现在 ROUTE 文本中；
3. 每个接收端的实际 SLL 顺序与计划一致，本地接收端不发生计划外绕行；
4. 静态接口、位置、引脚映射及 DFX 检查通过；
5. 清空旧 RM 后，属于静态段的有效 SLL 保持；属于旧动态实现的资源允许释放。

不能只扫描 `STUB` 后面的节点来判断全部无效资源：在反方向试验中，STUB 标记也可能出现在 SLL **后面**，上游 SLL 仍没有通向接收端。最终应以端点可达性和实际 PIP 路径为准。

报告应分别统计计划 SLL、实际物理占用 SLL、通向有效接收端的 SLL、仅占位的死支路 SLL。数量相同也不代表接收端分组和位置正确；物理占用比增量少/多同样不能独立判断实现质量。

### 4. 增量阶段继承已验证的静态段

静态侧 SLL 与 partition pin 作为冻结接口条件继承；活动 RP 内部 net 才生成新的 SLL 计划。不要重新施加整份旧全量计划，也不要为了对齐“原计划数量”恢复旧 STUB。

对 placer 而言，接口时序/线长模型也应加入 partition pin：静态侧按静态驱动与 PP，动态侧按 PP 与 RP 内 cell 分段计算。否则，即使只考虑 SLL 的位置，仍会遗漏 DFX 的必经物理接口。

## 验证状态

候选修复器尚未接入正式后端。当前结果支持根因定位和简单接口的修复方向，**不代表全部 94 条接口已修好**。

| 验证 | 实际结果 | 含义 |
|---|---|---|
| 原导出器，3 条接口独立诊断 | 3/3 导入无 STUB；布线后 3/3 被原审计拒绝 | 问题发生于路由阶段，不是 JSON/Tcl 导入就丢失计划 |
| 同位置、同周期，撤销这 3 条接口的约束 | 3/3 ROUTED，STUB=0 | 原生路由有可用解，但不会保留指定 SLL 位置 |
| 静态输入 `q1[10]`，补齐静态树 | ROUTED，原计划 SLL 与逐接收端审计通过 | 简单输入接口有效 |
| RP 输出 `A_address1[2]`，补齐静态树 | ROUTED，原计划 SLL 与逐接收端审计通过 | 简单输出接口有效 |
| 混合高扇出，第一版完整静态树 | 15 个节点冲突，route_design 失败 | 没有 STUB 仍不足以说明合法；该结果不算通过 |
| 混合高扇出，排除中继引脚/时钟节点 | 在限额内未找到可用连接，生成阶段拒绝 | 保持失败，不输出未经验证的候选约束 |
| 保留两个修正接口，复杂接口回退原生布线 | 复杂接口 ROUTED、STUB=0，两个修正接口再次通过原审计 | 三样本范围内可以采用显式混合处理，复杂接口的位置不再保证 |
| 清空两个旧 RM，再锁定静态 shell | 两个修正接口的计划 SLL 均保留，占用由 1→1 | 证明这两个静态 SLL 能跨过 shell 生成阶段；不是完整增量 PR 验证 |
| 两套新增 Tcl 单元测试 | 通过 | 覆盖 STUB 分支、接收端归属、共享树、无效 SLL、有限搜索与引脚排除 |
| 原有增量资源与作用域测试 | 14/14 通过 | 未破坏既有增量保护的单元测试；不是全量 DFX 验收 |

简单输入/输出的树构建分别为 0.423 s、0.347 s；对应局部 `route_design -nets` 为 72.938 s、54.967 s。复杂接口第一版构建为 47.728 s，受限修正版为 66.484 s 后拒绝。以上均为对应阶段计时，不能外推完整设计性能；没有把失败重试时间隐藏成算法加速。

shell 保留的精确资源为 `LAG_LAG_X60Y258/UBUMP19` 与 `LAG_LAG_X60Y269/UBUMP22`。输出接口在黑盒化后发生层次网名变化，物理资源仍由对应静态接口持有。该验证只覆盖两个已修正接口的 SLL 保持，没有验证完整设计的全部静态 PIP 不变、所有 94 条接口、更新后的两个新 RM 或完整 PR 检查。

### 可立即采用的保守处理与后续完整修复

- 对 DFX 边界接口，只有通过“无冲突 + 逐接收端实际路径”审计的约束才作为有效计划。
- 尚不能可靠构造的接口，显式撤销**该接口 net** 的旧 SLL/FIXED_ROUTE，交由 Vivado 原生完成；不需要关闭全部 E2 SLL 优化，也不需要撤销普通内部 net 的约束。
- 回退接口必须单列为 `native-interface-fallback` 结果，记录实际 SLL、容量与时序；不能仍记为“计划严格落实”。如果实验要求所有接口严格服从计划，则应停止验收，而非悄悄回退。
- 这个退路已在三个样本的无约束对照中验证能消除 STUB；未作为新默认策略写入正式后端。旧失败缓存不能直接改标为成功，应从修正后的全量布线重新形成静态 shell。
- 后续完整约束实现应优先复用 Vivado 已建立的合法接口骨架，在原生路由资源和 site 使用约束下连接计划 SLL；本次逐终点裸图搜索不足以覆盖复杂扇出，不能以增加无限重试替代合法性处理。

正式集成位置应在 `dfx_sll::apply_full`：普通内部 net 沿用已有导出器，DFX 接口进入 PP 感知的分段处理；实际 PP 和合法接口骨架宜批量提取，避免每条 net 单独启动一次路由。布线完成和静态 shell 封存分别验收一次，不能以导入成功替代这两个检查。该处理属于后端约束实现，不应放入每轮 QP 搜索真实布线路径。

### 本轮诊断脚本错误与真实失败的区分

早期一次候选 DRS 的末分支序列化不合法、一次传入空 `-exclude_nodes`，均属于本轮新增诊断脚本错误，已修正；不能据此判定原设计不可布。另有全计划逐项筛选、全器件节点查询、拥挤的已布线 DCP 上搜索过慢，已中止并记录。旧会话中的一个总计时变量被诊断脚本覆盖，相应总计时不采用；后续会话改用独立计时变量。

相对地，原接口约束出现 STUB、复杂静态树的 15 个节点冲突，以及受限搜索找不到安全路径，均为已记录的实际验证结果，不隐藏为通过。所有尝试保留在独立实验目录。
