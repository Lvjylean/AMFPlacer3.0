# 外部 floorplan 接入后的 AMF 耗时分解

本次 AMF 进程由 2222.076s 增至 2802.697s，多出 580.620s（9.677min，26.13%）。新增耗时主要出现在 **SLICEM 宏合法化的 legacy 二分图匹配求解**，不是读取外部 floorplan，也不是最终 CLB 打包变慢。初始化省了 21.005s；所有匹配求解累计增加 588.897s，其他工作合计反而减少 8.276s。

以下只分析已完成的 R10 和外部 floorplan 实验，没有重跑 AMF/Vivado，没有修改算法、参数或正式源码。条件核验与完整运行路径见 [时序比较报告](getrf-external-floorplan-vs-r10-timing.md)。

## 不重复计数的进程分解

单位均为秒。表中阶段来自两份 logs/amf.log 的顺序时间标记与 manifest 的 AMF 进程墙钟；各行互不重叠并回加到进程总耗时。

| 时间区间 | R10 无外部 floorplan | 外部 floorplan | 增量 |
| --- | ---: | ---: | ---: |
| 日志起点至聚类开始：输入、器件/设计初始化、初始宏识别等 | 28.513 | 28.522 | +0.009 |
| 聚类/SA 或外部 floorplan 初始化 | 24.972 | 3.967 | −21.005 |
| 全局阶段其余工作：QP、STA、诊断、阶段转换等合计 | 182.405 | 183.053 | +0.648 |
| 全局扩散区间累计 | 216.430 | 230.476 | +14.046 |
| 全局宏合法化区间累计 | 1344.158 | 1938.019 | **+593.861** |
| 最终 CLB 打包、异常处理、细化，至最终导出开始 | 400.364 | 393.484 | −6.880 |
| 最终输出、清理及进程/日志起点计时差 | 25.234 | 25.176 | −0.059 |
| **AMF 进程总计** | **2222.076** | **2802.697** | **+580.620** |

边界定义：
- 初始化为 Cluster Placement Start→Done；R10 其中 SA 自身只有 0.654s。替换掉的完整区间也仅占基线进程约 1.12%，可直接节省的时间很有限。
- 全局阶段为 Cluster Placement Done→ParallelCLBPacker: initialized，含首次 fixedCLB、五次 CLBElements、LUT/FF 增量配对及最终打包器构造。共 1742.993→2351.548s。
- 两轮五次 CLBElements 的实际迭代数均为 **10、6、6、6、10，总计 38 轮**；不是增加全局迭代数导致变慢。
- 扩散区间为每轮 WLOptimizer Done→Spreader Done；合法化区间为 Spreader Done→Legalization Done。可能含这些标记间的诊断/快照开销，不冒称纯算法计时。
- “其余全局工作”是扣除上述两个不重叠区间后的余额，**不能从现有日志进一步独立拆出完整 QP 和 STA 时间**。
- 最后一行残差同时吸收进程计时与日志计时的起点差；不将它全解释为 I/O。

## 宏合法化内部的直接计时证据

下表匹配求解来自每次 AMF_MATCHER backend=legacy ... solve_s 日志。所有调用都位于宏合法化区间内，诊断脚本检查了覆盖范围及每个区间的时间上限。

| 合法化分项 | R10 / s | 外部 / s | 增量 / s |
| --- | ---: | ---: | ---: |
| SLICEM / MCLB 匹配求解 | 1052.813 | 1646.346 | **+593.533** |
| BRAM/DSP 等硬宏匹配求解 | 117.607 | 114.348 | −3.259 |
| CARRY 宏匹配求解 | 45.521 | 44.143 | −1.378 |
| 合法化其余工作：候选搜索、建图、列处理、DP 等及区间诊断 | 128.218 | 133.182 | +4.964 |
| 合计 | 1344.158 | 1938.019 | +593.861 |

SLICEM 匹配调用为 91→95 次，BRAM/DSP 为 49→60 次，CARRY 为 40→38 次；合计 180→193 次。调用更多本身不代表更慢，例如 BRAM/DSP 总求解时间仍略降。

在 SLICEM 中，每次左侧节点为完整 **12,231 个 MCLB 放置单元**的调用，两轮都为 **31 次**：
- 累计求解 1051.726→1575.064s，增加 **523.338s**；单次平均 33.927→50.809s。
- 这部分已占进程净增量的约 **90.1%**，主要问题是同规模完整宏集合的匹配变贵，而不是多跑了全局迭代。
- 这些调用的平均右侧候选位置数反而为 26,025.2→25,148.9。不能用“候选顶点更多”解释全部减速；候选边连接关系、代价和并行子任务分布同样重要。

solve_s 使用 steady_clock，在 solve() 内围住各 legacy MinCostFlow 求解、并行等待和结果提取；不含此前的候选搜索与匹配器构造。外层合法化按顺序调用各求解器；累计的是每次调用的墙钟，不是把 OpenMP 各线程时间相加。R10 profiler 也记录 solve() 180 次、1215.945029s，与日志总和 1215.940190s 相差仅约 0.00484s，支持该定位。

## 为什么外部初始位置会影响它

当前外部 floorplan 接口替换的是初始化。其余全局布局和合法化仍然根据“当前放置单元位置→附近合法 site→候选边的 HPWL 变化代价”生成匹配问题。**代码相同，不代表输入给匹配器的图和边权相同**。

源码链路：
- [GlobalPlacer.cc](../../src/lib/HiFPlacer/placement/globalPlacement/GlobalPlacer.cc)：mCLBLegalizer 指向 SLICEM；宏合法化中调用此合法化器。
- [CLBLegalizer.cc](../../src/lib/HiFPlacer/placement/legalization/CLBLegalizer.cc)：getPUsToLegalize 选择 isMCLB 放置单元；findPossibleLegalLocation 选择 SLICEM site；createBipartiteGraph 使用 getHPWLChange 形成边权；未匹配完成时扩大位移窗口和候选上限再求解。
- [MinCostBipartiteMatcher.h](../../src/lib/HiFPlacer/problemSolvers/MinCostBipartiteMatcher.h) 与 [.cc](../../src/lib/HiFPlacer/problemSolvers/MinCostBipartiteMatcher.cc)：按候选图连通分量分配 legacy 最小费用流求解器，随后并行求解。因此图的连通结构、费用分布和任务不均衡可能影响耗时，左/右节点总数不足以描述难度。

首次粗合法化已经出现可量化的差别：

| 首次 SLICEM 粗合法化 | R10 | 外部 floorplan |
| --- | ---: | ---: |
| 首次待分配 MCLB 数 | 12,231 | 12,231 |
| 首次候选 site 总数（去重） | 9,673 | 7,256 |
| 第一次求解后仍未匹配的宏 | 5,972 | 7,052 |
| 完成本次粗合法化需要的匹配调用数 | 4 | 7 |
| 这组匹配求解累计 / s | 1.542 | 82.746 |

外部布局第一次求解后残留序列为 7052、5515、4540、3902、2668、1324，之后完成；R10 为 5972、2485、257，之后完成。这直接说明该时刻附近候选位置对宏需求的满足程度更差，需要更多扩大搜索和补配。它描述的是 **当前候选集合的局部竞争**，不代表全器件 SLICEM 总容量不足，也不代表 floorplan 被永久锁定。

因此，现有证据支持的解释是：外部初始布局改变了后续宏的空间分布及候选匹配问题，至少在首次粗合法化增加了局部分配压力，后续完整 MCLB 匹配也明显更耗时，抵消了省去聚类/SA 的收益。

尚不能确定这 523s/594s 中有多少分别来自连通分量变大、最小费用流增广/松弛次数变多、线程负载不均或共享主机竞争。两轮没有保存完整候选图及各 worker 的计数/时间，外部运行也未开启完整 profiler。故“耗时集中在 SLICEM 匹配”是实测结论；更深层求解器原因仍需专门计数或固定图重放才能定量确认，不能把单次差值全部归因于 floorplan 算法。

## 最终 CLB 打包为何不是主因

| 最终打包子区间 / s | R10 | 外部 | 增量 |
| --- | ---: | ---: | ---: |
| initialized→迭代打包结束 | 137.661 | 134.699 | −2.962 |
| 异常处理前的准备 | 1.637 | 1.606 | −0.031 |
| exceptionHandling 日志区间 | 68.825 | 79.284 | +10.459 |
| 后续时序细化、STA、槽位映射等至导出前 | 192.241 | 177.895 | −14.346 |
| 合计 | 400.364 | 393.484 | −6.880 |

第一轮 rip-up 待处理 PU 为 2542→4834，异常处理确实更费时，但后续细化减少抵消了它。不要将增加的约 10 分钟笼统说成“打包更慢”。
